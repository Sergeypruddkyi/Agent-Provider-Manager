- внутренние имена (`ClaudeProviderLauncher`, пространство имён, `.csproj`, `.slnx`, EXE) пока не переименованы и не совпадают с названием продукта `Agent Provider Manager` — это осознанное текущее состояние, а не ошибка документа;

- профили, пресеты, ключи и конфигурации Claude Code и Codex хранятся независимо; значение одного инструмента не переносится в другой;
- конфигурация Codex (`~/.codex/config.toml`) читается только для чтения; приложение не перезаписывает её и не удаляет пользовательские параметры;
- системные профили по умолчанию защищены от удаления и случайной перезаписи; идентифицируются по стабильному идентификатору, а не по отображаемому имени.

Если фактическая структура перестанет совпадать с этим разделом, сначала сообщить о конкретном расхождении и не придумывать новые пути.

## 1. Границы рабочей области

Агент работает только внутри `E:\Projects\Agent Provider Manager`, если пользователь явно не разрешил иное.

Без отдельного разрешения запрещено:

- сканировать диски (`C:\`, `D:\`, `E:\` и другие) в поисках файлов, версий и сборок;
- рекурсивно искать другие копии проекта или материалы за пределами текущего проекта;
- проверять исходники, конфиги, логи и сборки других проектов пользователя;
- читать внешние каталоги «для справки»;
- изменять или удалять файлы за пределами текущего проекта.

Если для задачи действительно нужен внешний путь:

1. назвать точный путь;
2. объяснить, зачем он нужен;
3. остановиться;
4. дождаться явного разрешения пользователя.

Наличие доступа к каталогу не является разрешением на его просмотр.

Единственное ранее согласованное узкое исключение: если пользователь прямо просит переиспользовать **только визуальное оформление UI** из `E:\Projects\YouTubeDownloader-Net10`, разрешено прочитать конкретные UI-файлы, необходимые для этой задачи. Это не разрешение сканировать весь проект, копировать его бизнес-логику или изменять его файлы.

- не додумывать состояние;

Выполнять только назначенную задачу.

Запрещено:

- добавлять функции «заодно»;
- начинать неоговорённый рефакторинг;
- самостоятельно переходить к следующему этапу;
- превращать одну задачу в длинную цепочку дополнительных задач;
- продолжать работу после установленного checkpoint без нового указания пользователя.

После существенного логического блока остановиться и сообщить:

- что сделано;
- какие файлы изменены;
- какие проверки выполнены;
- фактические результаты сборки и тестов;
- что осталось;
- можно ли переходить к следующему этапу.

Если проверка не пройдена — не маскировать ошибку заглушкой и не объявлять задачу завершённой.

**Не выполнять `git commit` или `git push` без явного указания пользователя.**

## 4. Приоритет работающего результата

Для задач, изменяющих приложение, использовать последовательность:

```text
изменение исходников
→ build/publish
→ запуск актуальной сборки из канонического каталога
→ проверка реального поведения
→ UI-проверка при необходимости
→ закрытие тестовых процессов
→ отчёт
```

Успешная компиляция сама по себе не подтверждает работоспособность приложения. Если задача затрагивает интерфейс, проверять опубликованную версию из `dist\AgentProviderLauncher`, а не случайную копию из промежуточного `bin`.

Не создавать дополнительные абстракции, инфраструктуру, зависимости и «заделы на будущее», если они не нужны для текущей задачи.

## 5. Каноническая сборка и публикация

Публикационная папка:

```text
dist\AgentProviderLauncher\
```

Основной проектный файл:

```text
src\ClaudeProviderLauncher\ClaudeProviderLauncher.csproj
```

Базовая команда публикации self-contained single-file для Windows x64 (запускать из корня проекта):

```powershell
dotnet publish "src\ClaudeProviderLauncher\ClaudeProviderLauncher.csproj" -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o "dist\AgentProviderLauncher"
```

Перед публикацией сверить фактическую структуру проекта и параметры `.csproj`; не менять их без необходимости задачи.

После публикации проверить наличие и время изменения:

```text
dist\AgentProviderLauncher\ClaudeProviderLauncher.exe
```

Правила:

- именно эту сборку запускать для пользовательской проверки;
- промежуточные каталоги `src\...\bin` и `obj` не являются дистрибутивом;
- не очищать `dist` вручную и не удалять дополнительные файлы (например `.pdb`) без выяснения их назначения;
- не применять команды и флаги, способные удалить пользовательские файлы;
- не считать случайный EXE из `bin` актуальной пользовательской версией.

Тесты проекта (при наличии и применимости):

```powershell
dotnet test "tests\ClaudeProviderLauncher.Tests\ClaudeProviderLauncher.Tests.csproj" -c Release
```

Если сборка падает из-за окружения, сначала сохранить полный текст ошибки и определить, связана ли она с проектом или окружением. Не менять исходники ради маскировки внешней ошибки и не искать другие установки SDK по всему диску без разрешения.

## 6. Обязательное правило расположения тестовых окон

**Любое видимое окно приложения, которое агент запускает для тестирования, необходимо размещать в правом нижнем углу экрана, а не по центру.**

Цель — не перекрывать пользователю центральную рабочую область и не мешать его работе.

Обязательные требования:

1. После запуска тестового приложения переместить его окно в правый нижний угол доступного рабочего стола.
2. По возможности уменьшить окно до подходящего размера, сохранив видимость элементов, необходимых для проверки.
3. Не оставлять тестовое окно по центру экрана и не перекрывать им основную рабочую область.
4. Если тест требует кликов, UI Automation или управления мышью, сначала разместить окно в правом нижнем углу и только затем начинать проверку.
5. По возможности использовать адресное управление окном тестового приложения (Win32 API, UI Automation, параметры запуска), а не перемещать его мышью через весь экран.
6. Не перемещать посторонние окна и не вмешиваться в приложения, запущенные пользователем.
7. Если окно нельзя безопасно переместить или уменьшить, остановиться и сообщить о препятствии, прежде чем выполнять тест, который будет мешать пользователю.
8. Не оставлять тестовое окно открытым после проверки, если пользователь явно не попросил оставить его для осмотра.

Правило распространяется на GUI-тесты, UI Automation, ручные проверки и любые другие тестовые запуски с видимыми окнами.

## 7. Закрытие тестовых приложений и процессов

**Агент не должен оставлять открытыми приложения, которые сам запустил для тестирования.**

После каждого теста:

1. штатно закрыть тестовое приложение;
2. дождаться завершения процесса;
3. проверить, что процесс действительно завершился;
4. если приложение зависло, перед принудительным завершением проверить PID и полный путь к EXE;
5. принудительно завершать только процесс, однозначно принадлежащий тестовому запуску агента.

Запрещено:

- завершать процессы только по совпадению имени;
- закрывать пользовательские экземпляры приложений;
- завершать процессы других агентов.

Учитывать дочерние процессы тестового запуска (в том числе консоль Claude Code, если она была запущена тестом), если они больше не нужны.

Если процесс нельзя однозначно идентифицировать, не завершать его автоматически — сообщить пользователю.

Перед завершением задачи проверить, что все тестовые приложения и процессы, запущенные агентом, закрыты. В отчёте подтвердить результат.

## 8. Конфигурации, пресеты и секреты

- Не менять логику провайдеров, запуск инструментов и хранение настроек, если это не входит в назначенную задачу.
- Именованные пресеты сохраняют **Base URL, API Key/Auth Token и Model** (текущая реализация: `%LOCALAPPDATA%\ClaudeProviderLauncher\presets.json`).
- **Working Directory задаётся отдельно для каждого проекта и не сохраняется в пресете.**
- API-ключ в пресетах шифруется Windows DPAPI (scope `CurrentUser`); не заменять это на хранение в открытом виде и не выводить ключ в логи.
- Переключение провайдера Claude Code изменяет только провайдерские значения в `~/.claude/settings.json`; исходный файл один раз сохраняется в `~/.claude/provider-manager/default-settings.json` и не перезаписывается. Сохранять этот механизм резервного копирования и возможность восстановления.
- Не перезаписывать глобальные конфигурации Claude Code или Codex без прямого указания пользователя и предусмотренного безопасного механизма.
- Перед изменением пользовательской конфигурации сохранять исходное содержимое и обеспечивать возможность восстановления.
- Не смешивать настройки Claude Code и Codex.
- Не записывать API-ключи, токены и другие секреты в Git, логи, тестовые данные, отчёты, README и демонстрационные файлы.
- Не добавлять Python, Electron, базы данных и другие технологии/зависимости без обоснования и согласования с пользователем.
- Сохранять фактический стек: C#, .NET 10, WPF, Windows.
- Не описывать детали реализации как подтверждённые, если они не проверены по исходному коду.

## 9. Независимость Claude Code и Codex

Целевое назначение проекта — управление провайдерами для двух инструментов: **Claude Code** и **OpenAI Codex**.

Требования к дальнейшему развитию:

- конфигурации, API-ключи, секреты и механизмы переключения двух инструментов должны быть независимыми;
- изменение, применение или откат настроек для одного инструмента не должны затрагивать настройки другого;
- нельзя переиспользовать один и тот же секрет или один и тот же файл настроек «по умолчанию» для обоих инструментов;
- общие компоненты (UI, хранение пресетов, выбор рабочего каталога) допустимы только при явном разделении данных по инструменту;
- поддержку Codex нельзя выдавать за существующую, пока она не реализована и не проверена;
- при реализации Codex действовать отдельной задачей, не смешивая её с правками Claude Code без указания пользователя.

## 10. UI и переиспользование компонентов

Если задача касается интерфейса:

- не менять основное окно и несвязанные элементы без необходимости;
- не добавлять библиотеку только ради оформления, если задача решается средствами текущего стека;
- не копировать бизнес-логику из других проектов.

Сохранять фактический технологический стек (WPF, .NET 10). Не менять его без необходимости и явного обоснования.

## 11. Критическая защита Git

Каталог `.git` — важные данные пользователя.

Без явного разрешения пользователя в текущем чате запрещено:

- удалять, перемещать или переименовывать `.git` и файлы внутри него;
- запускать `git init`, если репозиторий уже существует;
- выполнять `git reset`, `git clean`, `git stash`, `git gc`, `git prune` и другие потенциально разрушительные операции;
- удалять ветки или теги;
- переписывать историю;
- выполнять force push;
- запускать команды или скрипты, способные удалить, перезаписать или повредить `.git`.

Фразы «почини Git», «подготовь репозиторий», «сделай checkpoint» и «почисти проект» не являются разрешением на опасные операции.

Без отдельного разрешения допускаются безопасные операции чтения:

```text
git status
git branch -a
git log --all --oneline --decorate
git show
git diff
git diff --cached
git remote -v
git ls-files
```

Если потенциально разрушительное действие кажется необходимым:

1. остановиться;
2. назвать конкретную команду и последствия;
3. дождаться явного разрешения.

Если состояние репозитория не совпадает с предыдущим отчётом, сначала выполнить только read-only диагностику. Не использовать автоматически `checkout`, `switch`, `reset`, `clean`, `merge` или `rebase`.

Не выполнять `commit`, `push`, не публиковать релизы и не менять удалённые репозитории без отдельного указания пользователя.

## 12. Ограничение объёма изменений

Менять только то, что необходимо для текущей задачи.

Без необходимости не выполнять:

- массовое форматирование;
- переименование несвязанных файлов и классов;
- обновление зависимостей;
- крупный рефакторинг;
- изменение архитектуры;
- очистку файлов и каталогов.

Не удалять дополнительные файлы только потому, что они кажутся ненужными. Сначала установить их назначение и получить разрешение, если удаление не входит в задачу.

## 13. Итоговый отчёт

В конце каждой существенной задачи сообщить:

- какие файлы изменены;
- суть изменений;
- команду сборки/публикации, если применимо;
- фактические результаты тестов и UI-проверки;
- точный путь проверенной опубликованной сборки;
- известные ограничения и оставшиеся проблемы;

Не объявлять задачу полностью проверенной, если выполнена только компиляция, а требуемая проверка опубликованного приложения не проводилась.
